# kira 发布

本 skill 是项目发布流程的唯一入口。参数只提供候选信息，不等于发布批准。遵循「信息确认 → 日志审查 → 发布批准」三道关卡，每道关卡都等待用户回复后再继续。

## 1. 信息确认：第一次回复先问，再做事

首次调用只整理已知信息并询问，随后结束本轮；即使参数带版本号或写了「发布」，也先确认此次范围。不要在首次调用时修改文件、合并、提交、打标签、推送或触发 Actions。

一次询问本次尚未明确的事项：

- 版本与渠道：正式版、预览版或两者；让用户给出准确标签，例如 `v1.7.5`、`v1.7.5-beta2`，不自行递增版本。
- 代码范围：哪个分支/提交，是否先合并到 main；默认建议在 main 的最终发布准备提交上打标签，而不是日志更新前的旧提交。
- 预览版用户：发布正式版时，明确询问是否同时发布 beta，让预览版通道也收到更新；若是，让用户指定 beta 标签。
- 发布方式：只准备供审查，还是批准后推送并公开发布；平台范围按当前 workflow 提出建议，不擅自启动额外全平台构建。

用户已明确的项原样复述、不重复索要；至少让用户确认本次候选信息。涉及重发或补日志时也先确认目标与允许的补救范围。

**关卡完成：用户确认准确标签、代码范围、渠道覆盖及发布方式。**

## 2. 核查与准备

### 2.1 核查实际状态

读取当前 `pubspec.yaml`、`.flutter-version`、所选 `.github/workflows/` 及其 setup action、`lib/utils/app_update.dart`、`scripts/git-hooks/pre-commit`。配置是事实来源，遇到文档与实际行为不一致先说明。

- 检查工作区、分支、已有提交与 remote；取 remote 的真实仓库，不硬编码仓库名。
- `git fetch <remote> --tags` 后校验标签格式 `^v\d+\.\d+\.\d+(-[\w.]+)?$`，正式版不能带 beta 后缀。
- 本地已有目标标签：核实指向和推送状态，转入续发；远端已有目标标签：报告，不覆盖标签、不重复创建 Release。
- 网络失败保留原报错；只在系统代理已启用时按当前地址临时使用代理，不修改系统代理或持久 git 配置。
- 对无关未提交内容先停下确认；不自动 stash、reset 或混入发布提交。
- 合并经用户授权的源分支到 main。可快进则 `--ff-only`；分叉或冲突先报告，等待用户选择，避免自行决定 merge/rebase。

### 2.2 发布检查

- 本地 Flutter 版本、`.flutter-version` 与所选 CI job 必须一致，不一致时先修复并重新审查。
- `flutter pub get --enforce-lockfile`，随后 `git diff --exit-code -- pubspec.lock`。依赖从 pub.dev 获取，保持锁文件不变。
- 跑 `flutter analyze --no-pub`；只跑本次代码变化相关测试，全量测试需要用户单独明确要求。
- 报告通过、失败及未验证事项。检查失败时不进入发布批准；纯文档续发检查文档，不重复跑应用构建或全量测试。

### 2.3 准备版本与更新日志

先选正确基线，再收集 `git log <baseline>..<代码目标>`，核实需要的提交和历史日志：

- 正式版：上一个正式版本标签 → 本次发布代码目标。覆盖期间全部用户可见变化，不以最新 beta 作为正式版基线。
- 预览版：上一个 beta 标签 → 本次 beta 代码目标。无 beta 时说明回退范围并让用户确认。
- 基线必须是目标的祖先；版本排序仅用于候选，不能拿无关分支或未来标签当基线。

正式版将 `pubspec.yaml` 的版本主体改为用户指定版本，暂保留 `+NNN`；build number 由提交 hook 计算。按历史正式版风格整体覆盖 `docs/CHANGELOG.md`，它是本次正式发布的日志，不追加历史：

```markdown
- 🐛 fix: 简洁中文修复内容
- ✨ feat: 简洁中文新增功能
- 🎨 style: 简洁中文界面变化
- ⚡️ perf: 简洁中文性能改善

> [!TIP]
>
> 1. 必要的升级注意事项
```

- 按 fix → feat → style → perf 分组，合并同类描述，排除 CI、合并、重构、版本和纯文档提交；用户可感知的性能优化要保留。
- TIP 仅写确有必要的迁移/升级提示，不添加冗余说明。
- 普通开发不随手改 CHANGELOG；**本 skill 的正式发版准备必须更新 CHANGELOG**，不可用旧的「禁止修改」记忆跳过此步。
- beta 日志通常由 beta workflow 自动生成，不覆盖完整正式版 CHANGELOG。核查其实际区间、过滤规则与标题，向用户展示预计正文；缺漏先处理，不留到发布后。
- 双渠道核实两条日志及 build number；预览版实际比较安装包 build number，不仅看 beta 标签。beta 构建号须高于既有 CI 包，同一代码/同一构建号可同时服务两条渠道。

**关卡完成：展示完整正式版/预览版候选日志、准确区间、文件 diff 与检查结果，问用户是否认可，等待明确回复。此时不提交、不打标签、不推送。**

## 3. 发布批准：最后检查点

日志认可后，提交前给用户一份短清单：

- 正式版/beta 标签、main 上的代码目标及要加入的发布准备文件。
- 各渠道更新日志基线；确认 CHANGELOG 已包含所有获准条目。
- 哪些 workflow 将启动、产物及 Release 是否直接公开。
- 承诺先提交全部获准版本/日志，再将标签打在 **main 的最终准备提交** 上，并推送分支与标签。

明确询问「确认提交、推送这些标签并公开发布吗？」并等待。仅确认日志，不视为推送授权。若版本、代码范围、日志或平台在此后变化，重新展示对应变化并重新批准。

**关卡完成：用户明确批准这份清单中的提交、推送与公开发布。**

## 4. 执行发布

1. 只暂存获准的发布准备文件，提交 `chore: release <tag>`（其余规范服从项目）。默认分支上的发布准备编辑先在窄范围发布分支完成，再按获准方案合回 main；项目已启用的 hook 正常执行。
2. 接受 hook 对 `pubspec.yaml` 的 build number 更新，确认没有其他非预期文件；不跳过 hook、不回退自动版本变化。
3. 快进 main 到最终发布准备提交，重新确认 clean 状态、版本与 CHANGELOG。若用户指定现有提交打标签，只在该提交已包含获准版本和完整日志时继续，否则先解释并重新确认。
4. 创建 annotated tag。双渠道通常把两个标签打在同一最终提交，版本主体采用双方确认的应用版本；不为了 beta 标签擅自改应用版本字符串。
5. 再核实 remote 分支未前进、标签不存在、标签解引用等于最终 main HEAD，用 `git push --atomic <remote> main <tag...>` 一起推送。
6. 推送失败保留实际错误，先核实 remote 哪些操作已成功，再续做；不 force、不盲重试。

## 5. 构建与发布验证

推送标签仅代表发布已触发，不代表成品已发布。记录每个标签对应的 run ID、HEAD、URL。

- 用后台 `gh run watch <run> --exit-status` 等待完成，由完成通知唤醒；不另开轮询或 sleep。
- 某渠道构建失败：报告失败 job 和真实错误，不谎称该渠道发布成功。
- 正式版成功后，核对 Release 的 draft/prerelease 状态、全部预期安装包与构建号，并将远端 body 与获准 CHANGELOG 做换行规范化比较；正文不完整就报告并请求修正，用户已明确授权补正文时可直接修改并再核验。
- beta 成功后，按当前 workflow 检查固定 `CI` Release 的标题、prerelease、对应 build number 的 APK 与新增日志；仅存在 beta git tag 不代表预览版用户能更新。
- 双渠道分别报告，未完成的继续等待，不把一条成功当成两条成功。

**完成：两个渠道（或用户指定的单渠道）的构建、安装包、版本及正文均已核验，报告链接、tag/commit 与结果。**

## 续发与补救

先核实远端标签、运行中的 Actions 与现有 Release，保留已完成步骤：

- 未提交：回到日志审查和发布批准。
- 已提交未打标签：核实获准文件在目标提交，再续做。
- 已打标签未推送：核实内容和指向，任何更换目标都先让用户确认。
- 已推送/Actions 已启动：保留发布快照；后续 main 的 CHANGELOG 提交不会改变该次构建读取的文件。**已推送标签保持不可变。**
- 已推送后日志遗漏：先让用户审查完整正文、批准文档补交及远端正文修改；补交 main 的文档，等待原构建完成，再用 `gh release edit <tag> --notes-file docs/CHANGELOG.md` 同步并核验。不要声称补交能自动修复旧 run，不重打标签、不为正文重复构建。
- 预览版遗漏：确认独立 beta 标签及更新基线，重新通过日志审查和发布批准后触发 beta workflow。
